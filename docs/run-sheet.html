Ontada Connect

/ehr/connect

Show the connection card and the "Panel search" note. Don't press Connect — it will fail.

"The gateway is live and we can read its capability statement unauthenticated. Two things block the pull. Ontada supports authorization_code only, so a server can't authenticate itself — a person signs in once and the refresh token carries it. And our app registration is patient-scoped: one patient's record, no panel search."

If pressedThe login is blocked on one value — the redirect URI registered against our client. Loopback is refused by Ontada's WAF; anything unregistered is refused by the authorization server. It's visible in the Ontada portal and it's a one-line fix.

If you're asked

The four questions most likely to come, and short answers that don't oversell.

Is this real data or a mock-up?

Real. The coverage is a production 271 from UnitedHealthcare through Stedi, and our Stedi key is a production key — it reaches the real payer network. There are no fixtures in the codebase; the only seeded data is the cancer center and its facilities, which is tenant configuration an admin would type in on day one.

So when can we submit an authorisation?

Not through this integration. It needs a clearinghouse that carries X12 278, the payer's own portal, or a Da Vinci PAS endpoint where a payer offers one. That's a commercial decision and a contract, not an engineering task — worth naming an owner for it in the room.

What happens when Ontada connects?

The import is already built — Patient/$everything, mapped to a casebook, and where the bundle carries a Coverage resource it creates the pre-auth package with payer, member ID and group already filled. Temper expectations on the data though: the sandbox is backed by a store named test-ui_smoke, so expect a thin synthetic patient rather than a real oncology chart.

Can we put this in front of a customer?

Not yet, and for one reason that isn't about features: the backend has no authentication at all. Before real patients it needs auth, role-based access, audit logging on every record read, and a BAA. That work hasn't started.
